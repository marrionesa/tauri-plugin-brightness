Control display brightness from a Tauri application.

DDC/CI for external monitors, ddcutil for NVIDIA proprietary drivers and docks, kernel backlight for internal laptop panels. One API, three backends, and diagnostics that explain what to fix when a display is not detected. 

cargo add tauri-plugin-brightness
npm add tauri-plugin-brightness-api

Not an official Tauri plugin. It follows the Tauri plugin conventions, so it can be adopted upstream, but only codebases inside the tauri-apps organisation are official. TAURI is a trademark of The Tauri Programme within the Commons Conservancy.

Install

1 · Add the crates

[dependencies]
tauri-plugin-brightness = "0.1.0"

The engine lives in tauri-brightness-core, a crate with no Tauri dependency, so it can also be used from a plain Rust program.

2 · Register the plugin

tauri::Builder::default()
    .plugin(tauri_plugin_brightness::init())
    .run(tauri::generate_context!())
    .expect("error while running tauri application");

3 · Allow its commands

{
  "permissions": ["brightness:default"]
}

Narrower sets are available, such as brightness:allow-set-brightness alone for an application that should change brightness but not read it.

Usage

JavaScript

import {
  diagnose,
  listMonitors,
  setBrightness
} from 'tauri-plugin-brightness-api'

const monitors = await listMonitors()

if (monitors.length === 0) {
  // Explains which permission is missing
  // instead of failing silently.
  const report = await diagnose()
  console.warn(report.suggestions.join('\n'))
} else {
  await setBrightness(monitors[0].id, 50)
}

Rust

use tauri_plugin_brightness::BrightnessExt;

tauri::Builder::default()
    .plugin(tauri_plugin_brightness::init())
    .setup(|app| {
        for monitor in app.brightness().list_monitors() {
            println!(
                "{} is at {}%",
                monitor.name,
                monitor.brightness_percent()
            );
        }
        Ok(())
    });

Display identifiers

A display is addressed by a string that stays valid for the lifetime of a boot, and its prefix says which backend drives it:

IdentifierBackend
ddc-0, ddc-1DDC/CI over I2C, in process
ddcutil-1, ddcutil-2The ddcutil command line tool
backlight-intel_backlightLinux kernel backlight interface

Always use the identifiers returned by listMonitors(). Which backend wins depends on the machine, so they cannot be predicted.

Backends

Three backends are tried in order. The first is preferred because it stays in process; the second is the only one that reaches NVIDIA proprietary drivers; the third covers hardware that is not DDC/CI at all.

DDC/CI over I2C

Pure Rust through ddc-hi. No external process, so it is the fastest and the default.

External monitors on Linux, Windows and macOS.

ddcutil

The standard Linux DDC/CI tool. Slower, because every call spawns a process, but it handles what raw I2C access cannot.

NVIDIA proprietary drivers, USB-C docks, DisplayLink.

Kernel backlight

/sys/class/backlight, written through the org.freedesktop.login1 D-Bus interface, which needs no privileges.

Internal laptop panels, always enumerated as well.

Troubleshooting

Brightness control depends on permissions that are easy to get wrong, so the plugin ships a diagnostic command rather than failing silently. It reports exactly which piece is missing.

External monitors on Linux

sudo modprobe i2c-dev
sudo usermod -aG i2c "$USER"   # then log out and back in
sudo apt install ddcutil       # optional but recommended

Internal laptop panels

Nothing to configure. They are controlled through D-Bus without privileges, the same path GNOME, KDE and COSMIC use.

Frequently reported symptoms

The slider moves but the display does not change.
Check that DDC/CI is enabled in the monitor's own on-screen menu, then run ddcutil detect. If it lists displays, the plugin works with the same permissions.
No displays are detected on NVIDIA.
Install ddcutil and make sure the i2c-dev module is loaded, then log out and back in.
A display disappeared from the list.
Displays are re-enumerated on every call, so unplugging a monitor removes it immediately. Plug it back in and call listMonitors() again.

Repository layout

The engine is published separately on purpose: brightness control is useful outside a webview, and keeping the Tauri dependency out of the engine is what makes that possible.
